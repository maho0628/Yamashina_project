# ふりーむ投稿後改良を加えたところ、及びこだわりポイント
## テキスト文字送りアニメーションバグ修正及びオープニング、エンディングのローカライズ対応

 ふりーむ投稿時に文字送りのアニメーションのバグとして一瞬改行前のテキストが表示されてから改行されてしまうというバグがあった。
 シナリオ部分のローカライズ対応をしていく中で原因を探ったところ、スペースキーで改行ができるとチーム内では判断していたが、実際のところは一瞬半角の文字データが入ったと見なされて表示されてから、正しい改行が始まってしまうことが分かった。スペースを入れずに対応することも考えたが、言語によっては対応できたとは言えない対応だと考えた。そこで、スペースを入れた場合はそのまま文字送りのアニメーションを行い、改行そのものは文章内では絶対に使わない改行コードを入れることで対応した。

## スクリプタブルオブジェクトで設定するアイテム、選択肢が変動するイベントシナリオのローカライズ化対応

ローカライズをしていく上でスクリプタブルオブジェクト内で直接編集する方法でもありだが、その場合、実際に商品として出すとなった際にローカライズを行う翻訳者、プランナーがUnityを触る必要が出てきてしまい、その分連携など余計な時間がかかってしまう。そこで、Unity外で編集できるようにするにはどうすればいいのか色々調べていく中でGoogleスプレッドシートとの連携をプログラムを書かずに実現できるGoogle Sheets APIというものがあることが分かった。これとローカライゼーションアセットを組み合わせることで、Unity側で編集した内容はGoogleスプレッドシート側に反映、追加することができ、Googleスプレッドシート側の編集結果はUnity側にすぐに反映することができた。また、Googleスプレッドシート内の関数を利用することでグーグル翻訳を用いて自動翻訳対応を行うことができた。

# 制作後の反省点
- プログラム学習歴一年前後のみでプログラムを制作し、ふりーむに投稿後、別の人が制作したスクリプトを編集する必要があったこともあり、プログラム内に直接テキスト内容が記載されており、作業量も膨大であったため、一部でしかローカライズ対応を行うことができなかったこと。
 →今後は、ローカライズや将来的な修正を見越して、テキストデータはプログラム内に直接記述せず、外部ファイル（例：スクリプタブルオブジェクトなど）に分離して管理するようにする。

ここから下確認必要
- Googleスプレッドシート内で関数を使用していた際、翻訳対象のセルが空白または不正な値だったために #VALUE! エラーが発生し、それがそのままゲーム内に表示されてしまった。エラーハンドリングを事前に行っておらず、ゲーム内のユーザー体験に悪影響を与える原因となった。ローカライズデータを自動取得するフローにおいて、エラーや無効な値を検知・除外する仕組みが不十分だった。
→Googleスプレッドシート側で IFERROR を用いてエラー値を空文字やプレースホルダに変換することで、元データからエラーを取り除く。
Unity側でもスプレッドシートから取得した値に対してバリデーションを実施し、#VALUE! 等のエラー文字列を検出・除外または代替テキストに置換する処理を導入する。
ローカライズデータのインポート時に自動チェックを行うユニットテストや検証スクリプトを導入し、不正なデータを早期に検出するようにする。
